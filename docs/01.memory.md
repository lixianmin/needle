# 项目记忆

## 关键决策

- **2026-10-25 示例的业务接口统一挂 `/api/v1`，health / shell / 首页不带版本。** 版本号只出现在 `app/api/index.ts` 的 `API_PREFIX` 一处：先按版本分组（`v1.route("/login", ...)`、`v1.route("/bots", ...)`），组内路径是相对域名（`/get_bots`），升 v2 只加一个挂载，不动接口文件里的字符串。health/shell 不版本化：探针与运维面是部署配置里写死的一次性契约，Kubernetes 自己的 /healthz /livez /readyz 也在根上。旧路径不保留兼容。
- **2026-10-25 `trace` 补三个常用失败出口：`badRequest`(400) / `internalError`(500) / `unavailable`(503)。** 与 `notFound`(404) 一起构成业务 handler 的四个失败出口：状态码与 code 由出口锁死（与 `ResponseX` 同一套契约），业务只给 message——之前 handler 只能手写 `trace.json({code, message}, status)`，状态码散在业务里。`json` 保留给「成功但带自定义状态码」的场景。**不补 401/403/409/429**：401 由库的鉴权中间件产出，handler 不该自己判；其余业务里不出现，真要用再补。
- **2026-10-25 `traceOf` 返回的是类实例，九个方法挂在原型上。** 早先每请求现挂九个闭包（外加共享 context）全是堆分配；实测创建 81 → 45 ns、常驻 680 → 88 B/trace。代价：方法依赖 `this`，`const { json } = trace` 会抛 TypeError，要传就传 trace 本身。spec：`2026-10-24-request-log-and-parse-design.md` §5.2。
- **2026-10-25 日志写入路径 606 → 345 ns/条，核心不变量是「记录只在 `buildRecord` 里 sanitize 一次」。** 之前 `formatPayload` 又跑一遍（sanitize 占 68% CPU，整条记录走三遍），`buildRecord` 还靠 `delete` + `{...fields}` 收尾。新 sink 必须接受「收到的是 JSON 安全的纯数据」。spec §5.1.1。
- **2026-10-25 示例的版本号改成 git 版本，删掉写死的 `0.1.0`。** 口径 `git describe --tags --always --dirty`（仓库无 tag，所以是短 SHA；工作树脏时带 `-dirty`）。`bun run build` 走 `examples/honox-app/scripts/build.ts`，用 `--define __GIT_SHA__=` 烘焙进 dist（实测 bun build 不内联 `process.env`，所以不靠运行时 env）；`bun run dev` 不打包，由 `app/version.ts` 现跑 git；两者都没有才 `unknown`。镜像里没有 `.git`（根 `.dockerignore` 排掉，否则上下文翻倍），Dockerfile `ARG GIT_SHA` + 非空校验，缺了直接构建失败。测试 `test/git-version.test.ts` 钉住注入 / 本地 git / 无 git 三路。
- **2026-10-25 业务接口默认 POST + JSON body，`createApi` 不硬拦。** 理由两条：部分网关 / 老路由器只放行 GET+POST；嵌套对象、数组、可空参数在 query string 里表达不了。参数进 body 顺带缩小 URL 泄露面，但**不防日志泄露**——`trace.info(request)` 照样落盘，敏感字段仍要业务自己裁。query 分支保留给协议要求的 GET（页面、`/health`、SSE `/events`、Shell 的 `/log/:name`）；示例里的业务接口一律 `post` + bean（`GET /bots/get_bots` 已改成 `POST`，页面也不再提供方法选择）。

- **2026-10-25 示例加首页测试台（`/` + `/login`）。** 接口全在 JWT 后面，没 token 只能看到 401，「能跑」无法用眼睛确认。`res/web/home.html` 单文件零构建（`res/` 本来就进镜像，路径与 `res/config` 同一套 cwd 约定），启动读一次；`POST /login`（body `{user, passcode}`，走 `LoginBody` bean）校验 passcode 后签真 JWT（1 小时），只记 `{user, uid}`，不记 passcode / token——`trace.json()` 会把响应体落盘，凭据不能走它。两条路由都在白名单里。spec：`2026-10-25-home-test-console-design.md`。

- **2026-10-25 登录用固定盐的 passcode，只用于示例。** 客户端算 `sha256hex(DEMO_SALT + 密码)`，服务端只存哈希并用恒时间比较；用户名不存在与口令不对回同一个 401。**固定盐不防重放、不防离线爆破**，真实项目要每用户独立盐 + 一次性挑战（nonce / 短信验证码）。测试用户硬编码在 `app/api/login.ts`（`alice`/`alice123`、`bob`/`bob123`），查表用 `Map`——对象字面量会被 `{"user":"__proto__"}` 取到 `Object.prototype`。不动 `createAuthGuard`，登录逻辑不进 `packages/honox`。

- **2026-10-24 飞书消息照 Go 版 logo 的格式。** 用 `post`（不是 `text`）：标题 `[<Level>(<batch>) <titlePrefix>] <title>`、正文末尾带发送时间；`titlePrefix` 形如 `DEV honox-app 192.168.31.182:5001`。新增 `notify(level,title,text)` 做一次性发送（启动通知），绕过 `minLevel` 但仍过令牌桶——降 `minLevel` 会把所有请求日志都推进群。参考实现：github.com/lixianmin/logo 的 `lark/lark.go`。

- **2026-10-24 Shell 登录态 7 天、密钥与业务 JWT 分开。** 示例原来不给 `auth.secret`，库每次启动随机生成 → 重启后 localStorage 里的 token 全废，表现为「天天要登录」。改成显式 `shell.secret`（配置项，PRO 用 `APP_SHELL__SECRET`）+ `ttlMs` 7 天。**不复用 `auth.secret`**：两边 token 都是 HS256 + `sub`/`exp`，共用密钥会让面板口令变成业务接口的通行证。

- **2026-10-24 rid 改 ULID，Snowflake 只留给业务实体 id。** `@needle/got` 的 `src/id-tools.ts` 出 `nextUlid()`（26 位大写，48 位绝对毫秒 + 80 位随机）与 `nextSnowflakeId()`（13 位小写，需 nodeId）；`@needle/honox` 删掉 `snowflake` 选项与 `ids` 参数，rid 没带就 `nextUlid()`，也不转手导出 id 函数。理由：Snowflake 机器号只 10 位，MAC / IP 都是哈希进 1024 个桶，38 实例约 50% 撞号，且序列每毫秒归零 → 撞号即同毫秒重号。spec：`2026-10-24-honox-design.md` §8.4.1。
- **2026-10-24 日志目录不配置，固定 `log/`；飞书用 webhook 地址。** 示例 app 的 `app/logo.ts` 把 `createFileSink` 写到工作目录下的 `log/`（gitignore），不做 `logger.dir` 配置项——日志目录没有“每个环境不一样”的理由。飞书用 `logger.lark_url`（群机器人 webhook 地址，**地址即密钥**，仓库里留空；本地写在 `examples/honox-app/.env`，Bun 启动时自动加载，键名 `APP_LOGGER__LARK_URL`，模板见 `.env.example`）。顺手修了 logo 的坑：`secret: ""` 当 HMAC key 会抛 `DataError: Zero-length key is not supported`，而 send 的失败在 flush 里被静默吞掉——空串现在等同于没配。

- **2026-10-24 SSE 心跳 2 秒、无条件发。** 链路上最短的「无数据即断开」超时是应用服务器自己：`Bun.serve()` 的 HTTP `idleTimeout` 默认 10 秒（实测 10 秒掐连接、客户端 `ECONNRESET`）；原来的 15 秒 + 「空闲才发」让面板每 10 秒断一次、刷「连接失败」。心跳只存在于 Shell 的 `/events`，每个面板一个定时器，8 字节/2 秒可忽略。spec：`2026-10-22-logo-design.md` §8.2。

- **2026-10-24 日志面板按落盘格式渲染（`formatPayload`）。** 原来只渲染 `msg`，而请求日志是纯对象参数（不产生 `msg`），面板里只剩时间戳。现在级别 + `文件:行 [fn()]` + 紧凑 JSON 全上，栈例外（行下单独铺开）。面板与文件共用 `formatPayload`，`formatLine` = 时间 + 它。

- **2026-10-24 相对导入统一带 `.js`，目录导入写 `index.js`。** 包是 `nodenext`（tsc 不改写说明符，Node ESM 也不解析无扩展名/目录），所以 `import "./x.js"` 是硬要求；示例原本是 `bundler` 解析、写无扩展名，统一成 `.js` 只为「同一仓库一种写法」，顺带把 `"./api"` 这类目录导入显式写成 `"./api/index.js"`。

- **2026-10-25 覆盖率按「每包行覆盖 ≥ 90%」卡，`bun run coverage` 校验。** §11.1 从 80% 提到 90%，口径定为每包（`packages/*/src/`）行覆盖，不含 `dist`/`test`/生成物——bunfig 的 `coverageThreshold` 只认全局数字，全局 91% 底下藏着 shell 87.45% 正是要挡的，所以用 `scripts/check-coverage.ts` 读 lcov 逐包比（没出现在报告里的包算 0%，不静默跳过）。补测试后 shell 87.45 → 91.17，主要缺口是 `ui/fetch-adapter.ts` 的 `exec`/`fetchFile`/`authenticate` 三条真路径完全没有测试。已进验收命令（约 +13 秒）。
- **2026-10-25 变异测试：`--inPlace` 是硬约束，范围用 glob，阈值 ratchet 到 85。** TS 7 没有 `ts.parseConfigFileTextToJson`，Stryker 沙盒的 tsconfig 预处理直接崩，只能 `--inPlace`；测试必须 import `../src/*`（走包名测的是 dist，变异源码打不到测试，config.ts 曾因此 0 分）。`mutate` 从 8 文件硬清单换成 `packages/honox/src/**/*.ts` + `!types.ts`——清单里 `id.ts` 早已改名，Stryker 静默跳过，新增文件也永远不会进范围。加 `html` reporter（明细 `reports/`，已 gitignore）。**关掉 incremental**：它只按源码 diff 决定重跑，改了测试文件不会失效缓存，补强断言后分数仍是旧值（实测加了 4 条断言，增量仍报 141 个存活、`--force` 才是 125）。门禁跑 `bun run mutate`（全量，约 2 分钟），`--force` 保留在 `mutate:full` 里用于显式重建。当前 93.99%（break/low 93.7、high 95，并发 8 约 1.5 分钟），剩余 62 个存活突变体：excel 28 / auth 13 / config 8 / middleware 6 / node 4 / route 2 / mongo 1。**2026-10-25 起 logo 也进范围**：Stryker 只支持全局阈值，所以拆成两份配置（`stryker.conf.json` 管 honox、`stryker.logo.conf.json` 管 logo），各自 ratchet，免得 honox 的 93.7 被 logo 的欠账稀释；logo 当前 81.89%（break 81.8，约 6.5 分钟），199 个存活按文件分布与下一轮切入点见 spec 5.1.2；`bun run mutate:diff` 是改动过程中的快速反馈（只变异相对主分支改过的源文件，几十秒，不做判定），见 spec 5.1.3。已进验收命令（新增 worktree 没有增量基线，每次仍是全量；怀疑基线陈旧时手动 `bun run mutate:full`）；规则见 `AGENTS.md` §11「变异测试」。

- **2026-10-24 示例的接口文件精简到 2 个（health / bots）。** 一个领域一个文件、同文件挂多条路由（GET + POST），不再一个接口一个文件——文件数量不是覆盖度。`bots.ts` 里同时演示：query 取单条/全表、批量 POST + 部分缺失、`import { viper }` 取配置。

- **2026-10-24 配置不进 request context；logger 是唯一例外。** `HonoxEnv` 只留每请求独有的 `uid` / `user` / `authError` / `rid` / `api`，配置一律 `import { viper }`。`logger` 例外：`installMiddleware` 把装配时传入的 logger 写进 `HonoxEnv.Variables.logger`（context 键名也是 `"logger"`），`traceOf(ctx)` 依次取「显式传入 → context → 全局 `logo`」——否则 `createHonox({ logger })` 配的实例会被业务日志绕过，日志跑到全局 `logo` 去。2026-10-25 这个标识符从 `log` 统一改名为 `logger`（与 `createHonox({ logger })` 同名）。

- **2026-10-24 请求日志交给业务：`traceOf(ctx)`，中间件只兜 401/404/500/慢请求。** 自动两行日志删除：health 这类接口零日志，密码/超大字段由业务自己裁（中间件在路由前拿不到这些信息）。库兜四种——401（门禁分支）、404（notFound）、500（中间件读 `c.error`，业务替换 `onError` 也不丢）、慢请求（>1000ms，有 error 时不重复记）。`createApi("bots.ts")` 的 `logModule` 必填（值是源文件名，不是路由路径），经 context 进每条业务日志。spec：`2026-10-24-request-log-and-parse-design.md`。

- **2026-10-24 honox 的中间件链独立成 `src/middleware.ts`。** `installMiddleware(app, {logger, auth, public, slowMs})` 依次装 rid → 兜底日志（500 / 慢请求）→ JWT → 门禁，顺序由库固定；`index.ts` 只做装配（建实例、算白名单、挂 Shell、装 notFound / onError）。

- **2026-10-24 模型用 TS class 手写、schema 构建期生成。** 业务只写 `class BotsBody { ids: number[] = [] }`，`scripts/gen-models.ts` 生成 TypeBox schema + `registerModel` + 漂移断言（class 改了没重生成 → tsc 红）。生成器用 `typescript-6`（npm 别名 `typescript@6.0.3`）：项目编译器 7.0 是 native 版，`require("typescript")` 只导出 2 个 key，没有 AST API。只认字段声明，方法/泛型/任意联合/递归一律硬报错。spec：`2026-10-24-request-log-and-parse-design.md`。
- **2026-10-24 各包构建开 `declarationMap`。** dist 提交在仓库里，`types` 指到 `dist/*.d.ts`；没有 declaration map 时编辑器「跳转到定义」只能停在 .d.ts（甚至 JS）。开了之后 IDE 顺着 map 跳到 `src/*.ts`。代价：`.d.ts` 尾部多一行 sourceMappingURL，dist 里多 56 个 `.map`（也要提交，否则构建后 git 变脏）。
- **2026-10-25 只有 error 抓栈，定位靠手写 `module` 且只进行前缀。** 逐条抓调用点付了 `new Error` 的代价，打包后却只有 bundle 坐标（实测：源码 `bots.ts:2` → `dist/index.js:4` → minify 后第 2 行）。现在 `info`/`warn`/`debug` 零构造，`error` 带完整栈；`captureCallSite` 与注册期抓 `site`/`fn` 一并删除，`ctx.api` 只留 `{module}`。行格式 `日期T时间 [I] 模块名 {json}`，`module`/`site`/`fn` 只在前缀、不进 JSON（`site` 与 `module` 同义，都有时 `site` 优先）。判读仍用 `parseLine`。

- **2026-10-24 请求 id 叫 rid，入站有就沿用；对外一律字符串。** 读 `x-rid`，其次 `x-request-id`，白名单 `^[0-9A-Za-z._-]{1,64}$`；都没有才发号（发号实现见本节第一条：ULID）。入站值是外部输入，直接进日志行，不加限制等于允许伪造日志行。

- **2026-10-24 配置改成 viper 风格取值器，ENV 只认 dev/fat/pro。** `loadConfig` 返回 `Config`：`getString/getInt/getBool/getStringMap/get/has/raw` + `isDev/isFat/isPro`。`ENV` 是唯一由 loadConfig 读的环境变量，业务侧不再碰 `process.env`；其它覆盖走 `APP_*` 点分路径。取值缺省且无 fallback 即抛（比 viper 零值严）。示例的 Shell 账号来自 `server.shell_users`，镜像 `ENV=pro` + `app_pro.yml` 不写 auth.secret → 必须传 `APP_AUTH__SECRET`。

- **2026-10-24 示例的 HTTP 接口放 `app/api/`，一个领域一个文件（2026-10-25 路由改名为 `get_bots` / 新增 `get_bot_name`）。** `app/api/index.ts` 只做 `registerApis(app)` 登记，`app/main.ts` 不写路由；每个文件 `createApi("api/xxx")`，参数模型放 `app/beans/`。`bots.ts` 只挂两条，都是 POST：`POST /bots/get_bots`（body `{id?}`：带 id 取单条、空 body 取全表）与 `POST /bots/get_bot_name`（body `{id}` 回 `{name}`，查不到 404）；id 一律做参数不做路径段，业务参数不走 query。uid 由中间件写进 context；请求日志由业务用 `traceOf(ctx)` 自己写（见上面那条）。

- **2026-10-24 新增 `@needle/honox`：唯一允许依赖 hono 的包。** core/logo/shell 仍不依赖任何框架；no-hono 测试收窄为「honox 例外 + 源码扫描白名单（packages/honox、examples/honox-app）」。`createHonox()` 返回 Hono 实例，业务若用 HonoX 则 `createApp({ app })` 接入（spike 验证：父层中间件先跑、`c.get("uid")` 在文件路由里可读）。鉴权默认拒绝 + 白名单。spec：`docs/superpowers/specs/2026-10-24-honox-design.md`。

- **2026-10-24 honox 的元数据照 rim.server：扫目录 + sheet 名后缀分派。** 启动 `metadata.load(dir)` 扫 `res/metadata`：`*Template` 按 id 建表（第一层 key 是 sheet 名），`*Config` 取首个非空行当全局单例，其它跳过。代码里不写文件名、不写清单——新增表只加 `app/md/` 一个文件。manager 是显式实例（不是模块级全局），测试各建一个不串状态。`id` 只允许数字，缺 id / 非数字 / 重复 / 同名 sheet 跨文件都在 load 时报错并带 `文件#sheet` 与行号。hucre 只能异步读，所以必须启动预载、getter 同步。拆列靠「类即 schema」：模板写成 class，字段默认值 `equips: string[] = []` 即声明该列按 `|` 拆（元素 trim、保留 `"0"`、空单元格 `[]`），逐列换分隔符用 `static separators = { tags: "," }`；业务侧不写 `split("|")`。sheet 名取类名（`metadata.template(ApcTemplate)`），**构建不能开 `--minify`**（类名会被抹平，那时要显式补名字）。

- **2026-10-24 honox 示例不用 npm 的 `honox`（HonoX），TS 与根同版本。** 两者只是同名：示例把路由直接挂 `createHonox()` 返回的实例，`bun build` 打包，`export default { port, fetch }` 由 Bun 自己 serve。教训：HonoX 的岛检测（precinct → @typescript-eslint/typescript-estree）在 TS 7 上抛 `TypeError ... reading 'Cjs'`，带它就钉死 TS 5.9.3。示例仍不进 workspace（自带 tsconfig/lockfile），`@needle/*` 用 `link:`（`file:` 会让 `workspace:*` 解析失败）；`no-hono-coupling` 测试钉住「示例无 honox 依赖与 import、TS 与根同版本」。

- **2026-10-23 浏览器日志落 IndexedDB：`createIndexedDbStore()` 一个对象双身份（Sink + LogFiles）。** 手动接线：`logo.addSink(store)` 写、`logFiles: store` 读（BrowserShellOptions 零签名变更）；无 `log.export`，导出 = `log.list` 点开手动保存，与服务端同交互；tips 列表自带 sample（GONSOLE 同款，textContent 渲染防 XSS，服务端共用）；按级别级联出 info/warn/error 三个虚拟文件；保留 7 天 + 5000 条（时间轴锚设备时钟 + 入库 id 轴时钟无关）；库结构 v2 用 out-of-line 自增键（见教训）；一批一个 readwrite 事务，绝不逐条开事务。一切 sink 手动挂（服务端不自动挂 file sink）。Chrome 扩展 SW / 页面共享 origin 同一份 IDB（官方文档）；content script 的 IDB 属宿主页，不代写。spec：docs/superpowers/specs/2026-10-23-browser-log-store-design.md。

- **2026-10-22 传输用 SSE，不用 WebSocket。** WebSocket 在 Node 要 `ws`、在 Bun 要 `serve()` 时传 `websocket`、在 Workers 必须有 Durable Object 并改 wrangler 配置；SSE 只要一个 `(Request) => Response`，三处零接线。Workers 的 HTTP 请求没有 wall time 上限，够用。

## 经验教训

- **2026-10-25 性能结论必须来自 profile，而且 bench 的配置要和生产默认一致。** 先按 `batch:false` 量出「一条日志 595ns」，其实那是「每条立即 flush」的合并成本；生产默认 `batch:true`，建记录（`info()` 时）与格式化（flush 时）发生在两处，得分开量。归因也不要靠逐段猜：`bun --cpu-prof` 一轮就看出 sanitize 占 68% inclusive，整条记录被它走了三遍。

- **Hono `app.route(path, sub)` 返回父 app，路由在挂载那一刻拷贝。** `const v1 = app.route(...)` 拿到的不是子 app，后续 `v1.route("/login", ...)` 会挂到根上（`/api/v1/login` 反而 404）；先挂空子 app 再登记同样无效。要「前缀写一次 + 组内登记」：`new Hono().basePath(prefix)`，登记完再 `app.route("/", v1)`。

- **2026-10-25 `bun run example` 跑的是 gitignored 的 example dist，不是当前源码。** `examples/honox-app/dist/` 在 `.gitignore` 里，`bun run example` 直接 `bun dist/index.js`，而 `bun run build` 只重建 `packages/*/dist`、不碰它。症状：`/health` 200 但 `/`、`/login` 全 401——门禁先于路由，旧构建的白名单里没这两条，看上去像鉴权坏了。修法：拉代码后先 `bun run example:build`，开发直接 `cd examples/honox-app && bun --watch app/main.ts`；验收先打 `/`，只打 `/health` 骗得过（它在最早的白名单里）。

- **2026-10-25 `toMatchObject({})` / `toHaveProperty` 放过 `{id: undefined}`。** 「空串视为未传」的断言写成 `toMatchObject({})`，`parseQuery` 里 `filter(v => v !== "")` 的三个突变体全活——测试看着在测，其实什么都没测。空对象断言一律 `toStrictEqual({})` 或显式断言键集合；这种假绿只有变异测试抓得出来。

- **Hono 中间件里 `await next()` 对 Error 抛出不会抛。** compose 每层把 Error 交给 `onError`、设好 `context.error` 后正常返回；但非 Error 抛出、`onError` 自己抛错、自定义 `notFound` 抛错仍会穿过来。所以两路都要收：`c.error` + `catch`，且 `finally` 里用 `c.finalized ? c.res.status : 500`——没 finalize 的 `c.res` 会惰性造一个 200，把失败记成成功。

- **IndexedDB 的 keyPath 不能借用业务字段名。** `keyPath: "id"` 会让记录里的业务 `id` 直接变成主键：同 id 的两条日志互相覆盖（静默丢日志），`id: null` 还会让 `put` 同步抛 `DataError`、连带整批后半截丢失。修法：out-of-line 自增键（不传 keyPath）；结构变了要升 DB 版本、在 upgrade 里重建 store。测试用「同 id 两条都要在」+「id: null 不中断整批」钉住。
- **sink 的 close 不能吞掉 flush 已入队的批次。** `logger.dispose()` 是「先 flush（此时 sink 入队）再 close」；sink 若在出队时再查 closed，最后一批静默丢失——恰好是 pagehide 场景最需要的那批。修法：closed 只在入队时刻判一次，关连接排到队列末尾。
- **数据库连接必须挂 onversionchange 让路**，否则别的上下文升级会无限期 blocked；而 blocked 不能判成永久失败——对方让路后 onsuccess 仍会到来，那时要撤销 failed 接管连接，否则 store 永久降级。
- **测试写完要反证：把修复摘掉必须变红。** 本轮出现过两个摆设测试：一个 close() 与 open() 同轮导致 blocked 根本没触发，一个固定 sleep 掩盖了竞态。修法：先观测到目标事件再继续，固定 sleep 换轮询。
- **IndexedDB 事务内 count 排在 delete 之后，已包含删除效果，别再手工扣减。** prune 曾把 expiredKeys.length 再减一次，过期+超限同批时条数超上限（少删不丢数据，reviewer 抓出）。修法：直接用 count()。测试这类混合场景要专门覆盖——单轴各自有测试时，交叉路径恰恰没人钉。
- **fake-indexeddb 测试注入 now 方向别反**：now 要注入到记录之后一天（cutoff 落在记录之前），注入晚于 keepDays 会让每批写完即被过期清理清空，症状像「读路径坏了」，实际是清理按设计工作。
- **运行时能力探测不要用动态 import。** workerd 要求静态模块说明符，`import(变量)` 会在部署/运行时报 `ERR_MODULE_DYNAMIC_SPEC`。改用 `typeof` 能力探测；这类问题只有真跑 workerd（miniflare）才会暴露，Bun/Node 上测不出来。
- **写进代码注释的契约一样会烂。** `LoggerOptions.stackLevel` 的 JSDoc 写着「默认 warn」，实现是 `error`（`packages/logo/src/logo.ts`），两边对着干了很久没人发现；README 同一时期写的一直是对的。改法：改默认值的同一个提交里改 JSDoc，评审时对着实现读一遍 options 注释。
- **对外 API 命名先想对称。** `createShell` / `createBrowserShell` 一个带限定词一个不带，读的人得先猜哪个是服务端。定名按「跑在哪」成对来：`createServerShell` / `createBrowserShell`，类型同样成对（`ServerShell*` / `BrowserShell*`）。

- **不 await 的 `expect(p).rejects` 是摆设。** `serve` 的「close 后端口不可连」用它，断言从未执行；改成重新 `listen` 同一端口（EADDRINUSE 才失败）既真正生效，也不会被并发测试复用的 ephemeral 端口拖到超时。
